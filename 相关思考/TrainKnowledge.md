## 初始概念和交流
 
- **算法、模型结构和训练程序**，是 Agent 获得知识的方法。
- **训练后的参数、树结构、统计量等状态**，是经验形成的知识。
- **输入特征、适用范围、验证结果和更新规则**，决定这些知识什么时候能被正确使用。

所以，真正值得保存的知识单元，应当是：

$$
Ki={模型及其状态, 输入输出定义, 适用范围, 可靠性证据, 更新机制}
$$
它可以称为**外部可学习模型记忆**，作为暂定研究术语。

举个例子：一个长期运行的任务处理 Agent，可以保存“复杂任务通常耗时更久”这条文字经验，也可以从执行日志学习一个耗时预测器。后者能够根据任务类型、输入长度、工具选择和运行环境，对新任务给出预测，并随着后续真实耗时持续更新。

这里的价值在于：**经验形成了能对新情况作出判断的函数。** Agent 不需要每次把大量历史重新读进上下文。但模型记忆也有边界：它适合统计规律、预测和决策；精确事实、例外条款、原始证据，往往仍然需要文本或数据库。两者值得共同设计。


最有研究含量的问题是：**Agent 能否判断，什么时候值得把经验训练成一个模型，并在未来任务中持续获得净收益？**

这里至少包含三个具体难题。

1. **发现可学习的问题。**  
    从运行经历中识别重复出现的预测需求，定义输入、输出和反馈。例如发现“是否重试某个工具”可以学习，而不是每次临时推理。
2. **选择合适的知识表示。**  
    一条明确规则可能只需要文本或代码；复杂统计关系可能需要回归、树模型或排序器。样本很少时，训练模型也可能不如检索案例。
3. **管理模型的有效期。**  
    判断是否值得训练、是否优于现有策略、什么时候更新，以及环境变化后是否应停用或恢复旧模型。

“长期在线”会让这些问题更有意义，因为一次性训练只需要找到好模型；长期运行还必须支付探索、误用、维护和更新的代价。其中第三个最重要。审稿人很可能会问：

> 如果一个固定的在线分类器已经能解决问题，加入 Agent 带来了什么？

你需要用任务类型变化、特征变化、不同反馈形式，或者模型选择与维护的实验回答它。否则实验可能只证明传统机器学习适合这个数据集：长期迭代改进模型 + 模型适应变化的数据/规律；关于任务对象的知识：例如，用户偏好、文档相关性、业务数据规律等。


### 核心问题：什么经验值得变成模型

假设 Agent 长期帮助一个团队处理文档。运行过程中，它会积累几种东西：

| 积累的经验            | 合适的候选表示    | 后续如何使用    |
| ---------------- | ---------- | --------- |
| “这类文件必须经过负责人审核”  | 文本规则/可执行规则 | 检查明确约束    |
| 某份文档被退回的具体原因     | 原始案例       | 检索和核对     |
| 哪些文档更容易被退回       | 分类模型       | 预测新文档的风险  |
| 多项修改中，用户通常优先接受哪些 | 排序或偏好模型    | 排列修改建议    |
| 文档处理时间与内容、流程的关系  | 回归模型       | 估算耗时和安排工作 |

这张表体现了独特价值：**同一批交互经验，可以保留为案例、总结为规则，也可以训练成模型。Agent 需要根据未来用途进行选择。**

但需要注意，不能仅凭“这个问题看起来复杂”就决定训练。训练还需要可用样本、可定义的目标，以及足够多的未来调用机会。

因此可以把创建模型的条件分为三项：

- 可学习性：历史数据中是否存在能泛化的规律？
- 可验证性：是否能得到独立、可信的反馈，判断模型有没有学对？
- 可摊销性：未来使用次数是否足以抵消创建与维护成本？

这三个条件比“支持多少种机器学习算法”更适合作为论文的方法核心。

### “从案例到模型”的知识转化

最初没有模型时，Agent 使用基础能力和少量案例完成任务。随着交互积累，系统发现某种判断重复出现，就提出一个候选学习任务，例如：

> 根据文档内容和提交场景，预测用户是否会要求补充引用。

随后系统明确输入特征、反馈标签、候选模型和验证方式。只有候选模型在后续验证中表现出收益，才把它登记为可调用的知识。以后每次出现类似需求，系统可以选择直接调用模型、结合案例使用，或因不可靠而回到原有方法。

这里有两个容易被忽略的问题。

**第一，模型是在压缩经验，也是在舍弃信息。**  
分类器可能很好地预测“是否需要补充引用”，但它无法替代原始反馈中的理由和具体要求。因此，模型化之后仍应保留必要的证据索引，支持解释、纠错和重新训练。

**第二，模型的适用范围也是知识的一部分。**  
“这个预测器只在某个团队、某类文档、某段时间内验证过”，与预测器参数同样重要。模型库如果只保存名称和权重，后续很容易发生错误复用。

因此把模型记忆理解为：**一个带适用边界和验证证据的可学习函数。**

### 小模型与 LLM 的分工，可以比“调用工具”更紧密

小模型不一定要直接输出最终答案。它至少可以承担三种角色：

|角色|小模型提供什么|LLM 负责什么|
|---|---|---|
|预测器|概率、数值或分类结果|结合任务约束作出解释与行动|
|排序器|候选方案的优先级|生成候选、处理冲突和组织最终输出|
|环境模型|某种行动可能产生的结果|比较行动方案、制定计划|

我尤其看好**排序器**作为第一个原型。

例如，LLM 为文档生成若干修改建议，小模型根据用户历史采纳记录对建议排序，LLM 再组织最终呈现。用户之后的接受、拒绝或修改，又成为下一轮学习信号。

这个分工有几个适合做实验的特点：

- 小模型承担的目标明确，容易衡量。
- LLM 仍然负责语言理解与生成。
- 用户特有的规律可以在外部模型中积累。
- 可以同时观察预测准确性与最终建议采纳率。

不过，“没有采纳”未必等于“不喜欢”：也可能是用户没看到，或者当时没有时间。反馈定义必须仔细处理，否则系统会持续学习错误标签。

### 建议第一篇工作收窄到一个可证伪主张

可以暂定为：

> 在具有持续反馈的重复任务中，由 Agent 管理的外部模型记忆，能否在相同信息与预算约束下，提高长期任务表现，并降低累计执行成本？

这句话包含两个需要分别证明的部分：

- 模型记忆的价值：把历史转化成学习模型，是否优于仅保存和检索历史？
- Agent 管理的价值：让 Agent 决定模型的建立、选择与更新，是否优于固定训练流程？

我建议分两步实验。首先证明模型记忆本身有效，再开放自主管理。这样即使第二步没有收益，也能明确问题出在哪一层。

第一步可以把特征、模型类型和更新周期固定，只比较知识表示：

|实验组|可以积累什么|
|---|---|
|无记忆|不保留过去经验|
|文本记忆|累积规则和反思|
|案例记忆|检索过去的输入与反馈|
|模型记忆|用相同历史数据更新小模型|
|混合记忆|模型预测与案例证据共同使用|

第二步保持候选模型和数据相同，比较管理方式：

- 人工指定的固定更新策略。
- 简单阈值触发策略，例如每积累一定数量反馈就更新。
- Agent 决定何时创建、更新、切换和停用。

**如果 Agent 管理无法超过简单阈值策略，就应当承认这部分暂时没有贡献。** 这不会否定模型记忆，但能防止论文把系统复杂度误当成创新。

### 需要一个让“自主选择”有用、又不刻意偏袒它的任务环境

单一、稳定的分类任务，可能始终使用一个固定模型就足够了。要验证你设想的 Harness，需要让长期任务具备合理变化，例如：

- 一部分需求适合明确规则，一部分具有统计规律。
- 不同任务的数据量不同，有的不足以训练模型。
- 用户或场景发生变化，旧模型可能失效。
- 某类任务暂时消失，之后再次出现，可以检验旧模型复用。
- 部分反馈延迟到达，系统必须决定何时更新。

但这些变化应当来自真实使用场景，或作为明确标注的受控实验。不能专门设计一个让固定模型必败的环境，然后据此宣称普遍优势。

前面找到的 [StreamBench](https://arxiv.org/abs/2406.08747?utm_source=chatgpt.com) 已经采用连续输入与反馈来评价持续改进，可以作为起点；[LaMP](https://lamp-benchmark.github.io/?utm_source=chatgpt.com) 提供个性化任务，可以用于研究用户规律。若重新组织成在线序列或添加漂移，应单独报告为扩展协议，避免与原始榜单分数混用。

我认为最有说服力的结果会是这样的——这些是**期待验证的现象，并非已有结果**：

> 在冷启动阶段，系统主要依赖 LLM 和案例；随着可信反馈增加，部分重复判断逐渐由小模型承担。系统的累计表现改善，单次成本下降；环境变化后，系统能够发现旧模型不再可靠，并通过更新或回退恢复表现。

这样的学习曲线比“最终准确率提高了几个点”更能说明你的核心思想。

### 有一个实验，特别适合证明“模型确实成为了知识”

在 Agent A 的长期运行中积累模型记忆，然后：

1. 清空对话上下文。
2. 换成另一个冻结的 LLM 作为 Agent B。
3. 只移交模型、输入输出规范、适用范围和验证记录。
4. 测量 Agent B 在新样本上的收益。

同时设置文本记忆移交和案例记忆移交作为对照，并计入接口适配成本。如果收益能够跨会话、跨基础模型保持，就能支持一个很有意思的主张：**积累的能力具有独立于基础 LLM 的持久性与可迁移性。**

它仍然不能自动证明模型记忆优于所有其他表示，但能证明系统保存的东西确实可以被另一个执行主体使用。这个实验与“把模型作为知识”的概念非常契合。

目前最建议的落点是：**先做一个长期个性化任务，让 Agent 从交互反馈中形成外部排序器或预测器，再研究何时建立、何时更新、何时回退。** 候选模型保持少而清楚，把研究精力放在知识形成的条件、可靠使用和长期收益上。
