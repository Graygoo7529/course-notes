## 1. 范围与关键决定

当前单图算法以提交 14f7209 为已读实现基线：prepare → extract → stylize → compose。CNN 调节笔画筛选，颜色由固定色板生成。本阶段不训练、不微调、不增加新生成器，也不重新设计完整漫画算法。

| 项目 | 本阶段决定 |
| --- | --- |
| 桌面平台 | 先以 Windows x64 为实施假设，目标电脑硬件在实施时确认 |
| 手机平台 | 先做 Android ARM64；如果实际只有 iPhone，需重新选择运行时与采集适配 |
| CNN | 实时模式默认 MobileNetV3-Large；桌面单图研究入口保留四模型 |
| 桌面推理 | OpenVINO CPU 优先跑通；Intel GPU／NPU 作为设备实测后的选项 |
| 手机推理 | OpenVINO ARM64 CPU 先做小型可行性验证 |
| 应用 | React＋TypeScript 界面，Vite 构建，Tauri 管理本机能力与生命周期 |
| 视频目标 | 连续更新、低积压；不预先承诺 30 FPS |
| 保存结果 | 对冻结的原始帧执行完整样条精修，保存 PNG |

“同一应用框架”指复用界面与控制协议，不意味着摄像头、Python 环境和推理库可以原封不动跨平台运行。电脑上的 Python 可以快速复用已有实现；手机上推荐原生运行时和图像处理代码，不嵌入整套 Python／SciPy 作为首选路线。

## 2. OpenVINO 的实际适用边界

[OpenVINO 系统要求](https://docs.openvino.ai/2026/about-openvino/release-notes-openvino/system-requirements.html)列出了桌面平台、ARM CPU 与相应设备要求；CPU、GPU、NPU 的支持范围不同，设备驱动也不同。电脑端先显式选择 CPU，记录实际可用设备，再讨论加速。

[官方 Android 构建文档](https://github.com/openvinotoolkit/openvino/blob/master/docs/dev/build_android.md)给出了 Android 构建和 aarch64 示例。目前检索到的页面区分了 x86-64 预编译包与其他架构的源码构建；ARM64 手机不能使用 x86-64 动态库。实施时固定实际选用的发行版或提交，按照该版本文档确定 NDK、ABI 与最低 Android API，不照抄变化中的 master 示例数值。

因此，Android＋OpenVINO 是可验证的原生集成路线，不是安装一个前端依赖即可完成。先在目标手机加载 MobileNetV3 特征模型并执行一次，再投入完整手机界面。

没有依据保证 OpenVINO 可以使用目标手机的 Adreno／Mali GPU 或厂商 NPU；本方案以手机 CPU 为起点。也不把 macOS 支持推导成 iOS 支持。若 Android OpenVINO 在选定设备／版本上阻塞，可评估 LiteRT 或 ONNX Runtime Mobile 作为后备，但那是运行时路线变更，需保留同一模型权重与特征输出语义，并重新检查结果。

## 3. 核心算法：保留什么，改变什么

保持当前计算关系：

$$
S=0.5R_1+0.3R_2+0.2R_3,\qquad Q=E(0.25+0.75S).
$$

保留权重对应的输入归一化、三层选择、有效区域、单尺度 Sobel、以共享 E 确定阈值、几何区域阈值，以及固定色板。

新增的不是新的学习任务，而是三个运行机制：

1. **常驻模型**：加载、编译、预热一次，在会话内重复使用。
2. **两档渲染**：快速预览与高质量静帧导出。
3. **有界调度**：只处理最新帧，避免摄像头不断堆积任务。

视频模式不为每帧建立磁盘缓存，也不自动导出六格图或 run.json。短期状态放在内存；显式保存时再写图片与必要元数据。现有批量／缓存模式保留给课程对照实验。

## 4. 模型转换：导出特征，不导出分类结果

移动端选择现有 mobilenetv3_large_100.ra_in1k 权重，沿用已固定 revision。模型适配层输出三个特征张量，不能导出默认 1000 类 logits。

推荐顺序：

1. 在原 PyTorch 模型上固定三层输出及顺序。
2. 通过 OpenVINO 的 PyTorch 转换接口转换；直接转换若受依赖版本限制，再尝试 ONNX 中间格式。
3. 初版固定 batch=1，384×384 输入；通过后增加 256×256 的预览版本。
4. 为输入 layout、RGB 顺序、数值范围、mean/std、输出层名与 stride 写 manifest。
5. 同一张照片分别跑 PyTorch 与 OpenVINO，比较输出形状、特征差异、S、Q 和最终图片。
6. 先用 FP32 建立参照，再试权重压缩存储；不要把模型文件 FP16 自动等同于实际设备全程 FP16 计算或必然加速。

[OpenVINO 官方转换说明](https://docs.openvino.ai/2025/openvino-workflow/model-preparation/convert-model-pytorch.html)支持从 PyTorch 转换；实际依赖版本与模型算子仍需在锁定环境中验证。

**第一版只转换 CNN。** 相邻特征差、分位数归一化和图像处理继续由宿主执行，以减少首次迁移变量。运行稳定后，可将 L2 归一化、相邻差分一起封装进导出图，仅输出三张 D 图，减少高维特征从推理运行时复制出来的开销；分位数与有效区处理仍保留宿主端。此优化需要再次核对数值，不是第一阶段的阻塞项。

不做 INT8 校准或量化训练。当前没有必要为课程应用额外引入校准数据和质量变化分析。

### OpenVINO 运行策略

以 LATENCY 性能提示、batch=1 开始。推理请求、输入缓冲及图像缓冲尽量复用。异步 API 用来避免阻塞采集／界面，不等于单帧计算自动变快。

初版一个工作线程、一项在途推理即可；只有测量表明需要重叠时再尝试两个请求。不要照搬当前电脑的 6 线程到所有手机；设置线程预算，避免与 OpenCV 和关键点线程过度竞争。参考 [CPU 性能提示](https://docs.openvino.ai/2024/openvino-workflow/running-inference/inference-devices-and-modes/cpu-device/performance-hint-and-thread-scheduling.html) 与 [异步优化说明](https://docs.openvino.ai/nightly/openvino-workflow/running-inference/optimize-inference/general-optimizations.html)。

## 5. 实时预览与静帧精修

仓库上阶段记录中，MobileNetV3 的 CNN＋结构提取约 21～25 ms，颜色＋笔画约 264～435 ms；这些是作者电脑上的历史记录，不是手机预测。它们说明只加速 CNN 不足以解决整条链路延迟。

| 项目 | 快速预览 preview | 静帧精修 capture |
| --- | --- | --- |
| 工作尺寸 | 从 256×256 起步，必要时 320／384 | 沿用 384×384，之后再探索更高尺寸 |
| CNN 与门控 | 保留 | 保留 |
| 筛线 | NMS＋滞后连接，少量形态处理 | 当前完整细化与路径追踪 |
| 曲线 | 直接栅格线条；跳过逐路径 SciPy 拟合 | 有界样条平滑 |
| 抗锯齿 | 一倍或两倍画布，实测取舍 | 当前三倍画布 |
| 色板 | 同一固定色板 | 同一固定色板 |
| 阴影 | 不新增 | 不新增 |
| 输出 | 最新结果帧，不落盘 | PNG＋选定元数据 |

预览输出会与精修图略有不同，界面明确标为“实时预览”和“精修保存”。拍照时冻结一张原始帧，保存任务不得用一张旧预览放大冒充精修。精修期间可以暂停预览推理，原始摄像头画面继续显示。

改工作尺寸时，线宽、五官带宽、轮廓带宽和样条容差按尺寸比调整，面积阈值按平方比例考虑；不能只缩小图片，继续硬编码 384 画布上的 7／9 像素区域宽度。384 下保存的配置作为基准配置。

256 下低分辨率特征与量化结果可能损失细节，因此“降分辨率”是需样例确认的性能取舍，不是无损优化。

## 6. 视频稳定：先减少规则跳变，再增加时序算法

第一版不做稠密光流或复杂跟踪融合，先保持固定色板、固定模型与固定工作尺寸。对亮度增益、筛线阈值等标量做温和指数平滑，采用进入／退出条件避免欠曝开关反复跳动。

人脸关键点切换到对应平台的 VIDEO／LIVE_STREAM 处理方式，传入单调递增时间戳。优先让相机和关键点运行在同一帧坐标系；镜像只是显示选项，避免左右眼索引因翻转混乱。

几何过期时不能无限复用：快运动、人脸丢失或相机切换应禁用旧几何并重置状态。需要降低关键点频率时，设短有效期，仅对缓慢运动复用；这不是首版必须优化。

不要直接对连续输出图做像素平均，人物移动时会拖影；也不要把上一帧的 S 不经对齐地用于当前 E。首版每个被处理帧完整提取 S，保持规则清楚。

## 7. 应用架构与职责

| 层 | 技术 | 负责内容 |
| --- | --- | --- |
| 界面 | React＋TypeScript | 控件、布局、状态、错误提示、保存反馈 |
| 构建 | Vite | 前端开发与静态资源打包；不是推理服务器 |
| 应用宿主 | Tauri 2／Rust | 会话、权限范围、工作进程／原生插件、文件保存 |
| 桌面算法原型 | Python＋OpenVINO＋OpenCV | 复用现有函数，验证预览档与模型转换 |
| Android 采集 | Kotlin／CameraX | 连续帧、旋转、生命周期、背压 |
| Android 算法 | C++／OpenVINO／OpenCV | 本机特征提取、门控、快速渲染 |
| 几何 | 对应平台的 MediaPipe 接口 | 五官区域，失败时降级 |

Tauri 官方的移动插件机制允许 Kotlin／Swift 与 Rust 命令协作。手机上建议由插件控制会话并通过 JNI 调用 C++ 算法，不让高频原始帧绕行 React 状态。[移动插件文档](https://v2.tauri.app/develop/plugins/develop-mobile/)

React 不保存每帧像素为 state；结果画入 canvas，帧缓冲与句柄放在 ref 或独立控制器中。React state 只保存状态、参数和低频统计，避免每帧触发组件树重渲染。

## 8. 桌面第一版：优先复用现有 Python 核心

桌面先采用常驻算法工作进程：

- 前端通过 getUserMedia 请求摄像头，audio=false，video 播放原始预览。
- 用 requestVideoFrameCallback 在新帧到达时检查是否可提交；旧 WebView 不支持时提供节流回退。
- 把降到工作尺寸的帧送给常驻算法进程；模型不会每帧加载。
- 算法完成后返回结果图，canvas 显示；控制命令通过 Tauri 宿主管理。

[MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)要求安全上下文和用户授权。Tauri 中还需配置操作系统摄像头权限及具体 WebView 的权限响应；[localhost](http://localhost) 开发环境能运行，不代表打包应用一定能运行。应在早期测试安装包。

### 数据传输选择

快速原型可采用受控的本机二进制 WebSocket 通道：Tauri 启动 Python 工作进程，进程只监听 loopback 的随机端口，使用会话令牌鉴别连接，并检查来源。消息是元数据头＋二进制图像载荷，不用 JSON 数字数组和 Base64 传每个像素。

先用工作尺寸 JPEG 输入与输出打通，控制每次只一帧在途；但 JPEG 会影响边缘与色彩，要拿一张静帧对照原始数组路径。可接受后用于预览，精修保存传无损原帧；若编解码或复制成为瓶颈，再切换二进制 RGB／RGBA 和专用 IPC。跨 WebView 的零拷贝不能当成既成能力。

明确设置 Tauri CSP 的本机连接许可并在打包版验证；不开放整个网络范围。工作进程在应用退出时终止，错误和重启受宿主管理。开发时可用现有 Python 环境，交付桌面安装包时再封装工作进程及依赖，避免要求用户安装 Conda。[Tauri sidecar 文档](https://v2.tauri.app/develop/sidecar/)

这是桌面过渡架构；手机不沿用 Python sidecar。后续可将 C++ 核心用于桌面，统一更多代码，但不要求在摄像头初版前全部重写。

## 9. Android：原生采集与推理，复用前端控制

Android 第一阶段原型先完成“一张图片→OpenVINO→结果”，再接连续 CameraX。目标链路：

CameraX 分析帧 → Kotlin 插件 → JNI／C++ 图像处理与 OpenVINO → 最新结果缓冲 → 前端显示适配。

CameraX ImageAnalysis 使用 KEEP_ONLY_LATEST，分析线程及时关闭 ImageProxy；若异步使用缓冲，必须先复制或明确管理生命周期，不能关闭后继续读取。YUV_420_888 要正确处理 plane stride、pixel stride、裁剪和旋转，不能简单将 planes 拼接为 RGB。[CameraX 分析文档](https://developer.android.com/media/camera/camerax/analyze)

C++ 核心复用 OpenVINO 与 OpenCV。现有 NumPy 操作需要移植；SciPy splprep 不能直接打包成 Android 原生函数。移动实时版先跳过样条；若需本机精修，另做有界参数样条实现并用桌面结果核对，不能把 Catmull–Rom 或普通折线平滑称为原样复现 SciPy B 样条。

原始帧尽量留在原生侧；前端只接收降采样结果与状态。初版可从本机结果缓冲获取压缩二进制图像，吞吐不足再评估原生 Surface 叠层。原生纹理直接显示在 WebView 里不是 Tauri 自动提供的能力，需要额外平台适配；本阶段不以“跨平台零拷贝纹理”作为前提。

### Android OpenVINO 可行性闸口

1. 确认真实设备 ABI、Android 版本与可用内存。
2. 锁定 OpenVINO 源码版本，构建 arm64-v8a CPU Runtime。
3. 将依赖动态库、模型与 manifest 放入 APK／应用资源，初始化时准备可读路径。
4. 手机执行一次特征提取，检查三输出形状与 S。
5. 再测重复运行、内存和应用前后台切换。
6. 通过后接 CameraX 和 Tauri 插件。

如果第一到四步无法完成，先保留可用桌面版并定位运行时阻塞，不将手机调用电脑接口包装成本地推理成功。

## 10. 实时调度：最新帧优先

设置一个在途任务，最多保留一个最新待处理帧。新帧覆盖旧待处理帧，不排长队。桌面 WebView 原型也可以直接在忙时跳过采样，空闲后读取当前 video 帧。

相机 30 FPS 只说明采集频率。假如算法每帧用 200 ms，结果最多约 5 FPS；原始预览可以依旧流畅，但界面不能把原视频的 30 FPS 当作漫画 FPS。

每帧记录 session_id、frame_id、capture timestamp、config_revision。结果来自旧会话、旧相机、过期配置，或帧号早于已经展示的结果时丢弃。切换模型需取消旧会话、重新预热后再提交。

开始／停止状态机：idle → requesting_permission → warming_up → running → paused／stopped；任意阶段可进入 error。用户停止、应用进后台、页面销毁时，关闭视频 track、停采集、释放临时帧；恢复时重置时序滤波与帧号。

## 11. 最小接口

控制接口与帧载荷分开；下列为设计契约，不保证所有平台采用相同底层 IPC：

| 接口 | 用途 |
| --- | --- |
| initialize(config) | 加载模型、创建会话，返回 backend／model／输入规格 |
| start_camera(camera_id) | 申请权限并启动平台采集适配 |
| update_config(revision, style) | 更新色板、密度、质量档；不重新加载模型 |
| pause／resume／stop | 控制资源与队列 |
| capture_and_render | 冻结原始帧并执行精修 |
| save_result(result_id) | 按平台规则保存图片 |
| get_status | 返回模型状态、最近错误与低频性能统计 |

FrameMeta 包含 frame_id、session_id、config_revision、width、height、pixel_format、rotation、mirrored 与时间戳。输出包含相同 ID、结果载荷、阶段耗时、关键点状态。像素由二进制通道或平台缓冲传递，不塞进普通参数 JSON。

前后端时间戳属于不同进程时不能直接相减。端到端展示延迟在同一前端单调时钟上记录提交和显示；原生内部各阶段使用本机单调时钟。需要采集到显示的真实延迟时，再建立共同时间基准或校准偏移。

## 12. 界面与可视化

默认只展示原始预览与漫画预览，移动端使用单一主画面加原图／漫画切换，避免过多控件挤压画面。

主要操作：开启摄像头、暂停、前后摄像头切换、线条密度、自然／粉彩色板、拍照精修、保存。桌面研究模式可额外选择四种 CNN；手机仅一个模型，不展示无效选择项。

调试抽屉展示当前后端、工作尺寸、实际漫画更新 FPS、处理耗时、提交到显示延迟、丢帧数、关键点状态。统计每秒更新即可。六格过程面板只在暂停或单次拍照时生成，不每帧导出。

前置摄像头是否镜像作为显示配置，保存时明确采用哪一种方向。原图与漫画预览必须采用一致变换，否则看起来像左右错位。

## 13. 性能预算与完成标准

设处理时间为：

$$
T=T_{\mathrm{convert}}+T_{\mathrm{prepare}}+T_{\mathrm{face}}+
T_{\mathrm{cnn}}+T_{\mathrm{structure}}+T_{\mathrm{render}}+
T_{\mathrm{transport}}.
$$

端到端还包含队列等待与显示。异步可重叠部分阶段，但不会消除计算成本。

先以每秒 10 次漫画更新、约 100 ms 处理预算作为探索目标，而不是交付保证；不达标时先减少渲染与尺寸开销，允许清楚标示实际 5～10 FPS 的课程演示。达到 15／30 FPS 分别需要约 66.7／33.3 ms 的串行处理预算，不能凭 CNN 的单独耗时推算。

检查保持轻量，服务于工程正确性：

- 一张固定图片核对 PyTorch 与 OpenVINO 输出层、S、Q、最终图。
- 数值差不只看平均值：阈值附近微小误差可能改变线条，必须看实际成图。
- 持续运行数分钟，观察延迟是否积压、内存是否增长、手机是否明显降频。
- 拒绝权限、相机占用、前后台切换、快速拖动参数、停止重启都能恢复。
- 断网条件下确认模型在本机运行；保存的图片对应用户冻结的帧。
- 分开报告冷启动、预热后算法耗时、漫画更新率和保存耗时。

这不是大规模模型评估，不安排人工质量打分或性能排行榜。

## 14. 推荐实施顺序

| 里程碑 | 最小交付 | 继续条件 |
| --- | --- | --- |
| M1 OpenVINO 桌面单图 | MobileNetV3 三层输出＋原渲染 | 结果与当前 PyTorch 路径相符 |
| M2 预览档 | 256 栅格预览与 384 样条精修 | 单图质量可接受，阶段耗时清楚 |
| M3 Tauri 桌面相机 | 开启、连续处理、停止、保存 | 安装包能授权，最新帧策略有效 |
| M4 Android 运行时试验 | ARM64 手机单图推理 | 模型及原生库加载成功 |
| M5 Android 摄像头 | CameraX＋本机处理＋React 控件 | 丢帧不积压，旋转镜像正确 |
| M6 演示整理 | 桌面／手机录屏和参数记录 | 如实说明实际 FPS 与实现档位 |

M4 可在 M1 后尽早单独验证，以免桌面界面完成后才发现手机运行时阻塞。桌面摄像头打通前不要求四模型都完成 OpenVINO 转换；移动端不加载四个模型。

建议目录职责为：现有 Python 核心保持参考；新增模型导出工具；apps 下保存 Tauri／React；native 下保存 C++ 核心与 Android 插件；models 下使用 manifest 管理转换产物。沿用用户本地修改→GitHub→助手读取的协作方式，本文仅交付设计，不写回仓库。
