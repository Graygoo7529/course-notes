# 技术路线评审

评审日期：2026-11-09。依据本地技术路线、上游官方源码、本机环境检查以及第一、二阶段试运行。当前结论覆盖离线单帧与本机 Web 摄像头闭环；尚未做 GPU 加速与多机部署的性能验收。

## 1. 结论

方案合理可行，覆盖“摄像头、多脸检测、逐脸素描、帽子库、佩戴变换、Web 展示”全部要求。推荐保留 YOLOv5s-Face + 独立素描生成器 + 二维帽子主线。先完成本机浏览器应用，随后再决定是否增加远程访问。

素描主线已经确定为 Informative Drawings 的 `anime_style`（Lineart fine）。本机 CPU 试跑能够加载权重并生成完整线稿；`opensketch_style` 保留为风格对照，U²-Net Portrait 暂作可选遮罩候选。APDrawingGAN++ 暂不进入安装范围。

第一、二阶段已完成 YOLOv5-Face → Lineart fine → 淡彩帽子整帧合成，并接入摄像头、trackId、帧间关联和同帧冻结拍照。

## 2. 设计中合理的部分

| 决策 | 为什么合理 |
| --- | --- |
| YOLO5Face 专用权重 | 直接获得人脸框与五点，符合 YOLOv5 作业条件；普通 COCO 模型不能替代 |
| 检测与生成分开 | 两个预训练模型通过裁剪照片连接，避免任意拼接不兼容的特征与解码器 |
| 保存裁剪变换 T | 原始关键点、素描和帽子共用坐标；已对齐后不重复施加原始 roll |
| 按 ID 平滑几何 | 减少裁剪抖动，不直接混合图像造成拖影 |
| 独立占据遮罩 | 白脸区域仍然遮挡后帽层，不能用线稿反色充当透明度 |
| 单帧在途与冻结拍照 | 不积压旧帧，保存时能保证多人来自同一时刻 |

YOLO5Face 的检测实现需要分别还原框与五点坐标；相似变换前须统一 letterbox、镜像和左右语义。[官方检测代码](https://github.com/deepcam-cn/yolov5-face/blob/master/detect_face.py)

## 3. 需要补足的边界

**五点不构成脸轮廓。** 原方案“用关键点轮廓构造遮罩”需要明确关键点来自哪里。第一版只用 YOLO 五点时，用框与眼线估计头部椭圆/头顶区域，明确它是近似遮罩。需要可靠轮廓再增加 MediaPipe；它不是头发分割，无法独自解决帽檐、头发和侧脸的全部遮挡。

**帽子空间与生成输入应分开。** 给帽子留下显示空间是必要的，但不要把大量头顶留白都压进 256 人像输入，导致脸部有效像素过少。保持生成裁剪的稳定人像占比，再扩展合成画布；帽子超出原裁剪框时不能被裁掉，两种画布变换都计入 T。

**“合适”应可解释。** 默认按素材支持的视角、脸宽比例选一个可佩戴帽子，绑定 ID；用户可手动换款。只有 roll/五点时先做正面佩戴，不把鼻尖偏移包装为精确三维姿态。自动默认选择可以作为完成题意的一部分，不必引入审美或性别分类。

**多人需要自己的时间状态。** 第一版用 IoU、归一化中心距离和门限做关联，遇交叉允许 ID 重建。平滑参数随真实时间间隔更新，例如 α=1−exp(−Δt/τ)，避免 2 人和 4 人处理帧率不同时平滑强度失控。需要 MediaPipe 时，不能把不同人的裁剪交替送入同一个有状态 VIDEO 实例；可先用无状态 IMAGE 调用，再按 trackId 自行平滑。官方也注明多脸模式不能直接期待单脸模式的内置平滑。[MediaPipe 配置](https://developers.google.com/edge/mediapipe/solutions/vision/face_landmarker?tab=Python)

**所有有效检测都需要明确结果。** 可降低整体更新率或按 batch 分批，不静默只取前几张脸。远处小脸即使检出也未必有可辨认素描；界面应保留检测并说明画质限制。平滑不能保证生成器自身的时间一致性，静止视频仍需要实际查看线条闪烁。

**Web 的部署范围先定为本机。** 浏览器 `localhost` 摄像头 + 本机 FastAPI 足够交作业。后续手机访问电脑的普通局域网 HTTP 地址通常不满足摄像头安全上下文，需要 HTTPS/WSS。这里的手机网页也仍然使用电脑推理，并不等于手机端模型部署。[摄像头接口要求](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)

## 4. 模型与旧代码适配

- Informative Drawings 的测试脚本用 3 个残差块，构造类默认是 9；应按权重实例化。测试脚本存在直接 `.cuda()` 调用，CPU 模式须由适配器改为 `.to(device)`，不能照抄命令就声称支持 CPU。推理只需要生成器，不需要 CLIP、深度模型或判别器。[推理脚本](https://github.com/carolineec/informative-drawings/blob/main/test.py)
- U²-Net 必须用 `u2net_portrait.pth`。先对齐官方 512 预处理与反相、归一化；再测试降尺寸。近常数输出的极值归一化应防止除零。人像生成权重与分割权重不是同一任务。[人像推理脚本](https://github.com/xuebinqin/U-2-Net/blob/master/u2net_portrait_test.py)
- YOLO5Face 旧检查点加载依赖其模型类；PyTorch 2.6 起 `torch.load` 默认 `weights_only=True`，上游整模型加载需要局部兼容处理。后续仅对核实来源的官方检查点显式处理，不能全局关闭加载限制。[YOLO 加载器](https://github.com/deepcam-cn/yolov5-face/blob/master/models/experimental.py)、[PyTorch 序列化说明](https://docs.pytorch.org/docs/stable/notes/serialization.html)
- 上游旧环境文件不直接覆盖现有 d2l。NumPy/Pillow API 和顶层模块名称冲突在适配器中逐项修正；源码版本与权重哈希需记录。安装成功和文件下载完成都不等于模型已验证。

## 5. 实施范围

当前机器识别到 RTX 4060 Laptop、约 8 GB 显存，具备尝试 GPU 多人推理的硬件条件；但 d2l 当前为 CPU torch。性能瓶颈很可能在多人的素描生成与编解码，不能只引用 YOLO 论文 FPS。先测 1／2／4 人端到端时间，再决定 batch、输入尺寸和刷新率。

先交付“逐人卡片 + 同帧戴帽 + 冻结保存”，再增加按原画面位置排列的多人纸面合成。先准备 3 款正面帽子，侧面素材、细头发遮挡和三维深度关系作为边界，不引入训练任务。

上一项目可复用相机生命周期、单帧调度、会话/配置丢弃规则和移动布局经验；新的素描生成器与多人状态管理应独立实现，不沿用单人渲染结果冒充多人生成。

## 6. 本地实测与 API 冒烟

当前离线入口是 `scripts/run_core_demo.py`。它加载本地 YOLOv5-Face 和 Lineart fine，先把输入缩到长边 512，再进行检测、整帧线稿和淡彩帽子合成；使用 `--cards` 时，复用同一帧检测结果生成逐人肖像卡片。

在实验包附带的公开 Apollo 11 三人照片上，YOLOv5-Face 检出 3 人，置信度约为 0.83、0.87、0.86；整帧线稿、三顶帽子和 3 张卡片均生成成功。Grace Hopper 单人示例检出 1 人，置信度约 0.85。输出位于被忽略的 `outputs/core_demo/` 和 `outputs/core_demo_apollo11/`。

当前 CPU 处理时间包含模型预处理、检测、整帧 Lineart 和合成；启用卡片时还会为每个人再运行一次 Lineart。本地 WebSocket 冒烟已验证场景帧、拍照卡片和断开清理，但这仍不代表 CPU 摄像头已达到目标帧率。后续可按硬件条件调整整帧线稿更新频率、批量大小和前端发帧周期。
